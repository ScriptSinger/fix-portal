# Повторная обработка Telegram updates

Webhook сохраняет payload и ставит `ProcessTelegramUpdate` в стандартную очередь.
Для асинхронной обработки нужен `QUEUE_CONNECTION=database` и работающий `queue:work`.
Миграция добавляет только структуру: поле `next_attempt_at`.

Воркер атомарно резервирует update на пять минут; его timeout — 60 секунд.
Успешный update больше не обрабатывается. Ошибки сохраняются в `processing_error`.
Максимум пять попыток на update, интервалы после ошибок: 60, 300, 900, 3600 секунд.
Остановка воркера также расходует попытку; после истечения резерва событие доступно снова.

Планировщик каждую минуту запускает `telegram:updates-retry`: возвращает в очередь
необработанные события, включая потерянные при сбое постановки в очередь.
Монитор `telegram:webhook-monitor` продолжает сообщать о зависших и исчерпавших попытки событиях.

После устранения причины ошибки можно начать новый цикл попыток для одного update:

```sh
php artisan telegram:updates-retry --update=123456
```

Команда не сбрасывает активный резерв или ещё не истёкшую паузу и не повторяет успешно завершённые события.
При развёртывании выполнить миграции и перезапустить воркеры (`php artisan queue:restart`).

Повтор обработки не гарантирует однократную отправку внешнего сообщения: если Telegram
принял запрос, но ответ потерян, повтор может отправить сообщение снова.
Сохранённый вопрос при повторной отправке кнопки подтверждения не дублируется.
